Список оптимизаций claude-web

На основе аудита кода (daemon, server, frontend, безопасность), отсортировано по серьёзности, с указанием места и способа исправления

Статистика: всего 28 проблем. CRITICAL 4 / HIGH 7 / MEDIUM 10 / LOW 7
Ключевые области: устойчивость процесса daemon, блокировка цикла событий в server.py, неограниченный рост DOM во фронтенде, CSRF в режиме мобильного доступа
Принцип: наша архитектура (постоянный демон Node + 8 параллельных runtime + протокол 4-байтовых фреймов) лучше, чем у конкурентов. Проблемы в шлифовке деталей.

I. Демон Node (daemon.mjs + agent_sdk_bridge.py)

СерьёзностьПроблемаМестоВлияние / что замечает пользовательСпособ исправления
Устойчивость процесса
CRITICAL Нет подстраховки uncaughtException / unhandledRejection daemon.mjs целиком Любое необработанное исключение SDK сразу убивает daemon, все 8 активных сессий падают Добавить process.on('uncaughtException/unhandledRejection'): завершать текущий turn + писать error+done, daemon продолжает жить
CRITICAL Нет перехвата process.exit() daemon.mjs целиком Если SDK внутренне или зависимый пакет вызовет process.exit(), daemon умирает без предупреждения Переопределить process.exit = (code) => { throw new DaemonExitInterrupt(code) }, перехватывать во внешнем catch в handle()
HIGH Нет мониторинга сиротства PPID daemon.mjs целиком После kill -9 / OOM процесса Python daemon становится зомби и никогда не завершается, занимая порт и память setInterval каждые 5 секунд проверяет process.ppid; при значении 1 или ESRCH — graceful shutdown
Параллелизм и гонки
CRITICAL abandon_turn сначала удаляет queue, затем отправляет interrupt, кадр done теряется agent_sdk_bridge.py:390-394 Все последующие turn этой session падают: "A Code turn is already running", в течение 30 минут до освобождения по простою Сначала отправить interrupt → дождаться прихода done (с таймаутом) → затем удалить queue
CRITICAL Гонка между interrupt и readRuntime write() daemon.mjs:417-448, 613 interrupt возвращает ok, но turn не выдаёт кадр done, session зависает При interrupt сначала установить флаг aborted → цикл readRuntime проверяет флаг → гарантировать обязательную отправку done
HIGH Между preflightSend и handleSend есть окно времени, которое может пересечь параллельный send daemon.mjs:586-604, 869 Оба turn одной session получают accepted, события смешиваются, session повреждается Объединить preflightSend + accepted + handleSend в одну атомарную операцию внутри одного withRuntimeMutation
MEDIUM При сканировании простоя disposeRuntime не await, старый reader может записать уже переиспользованный requestId daemon.mjs:888-893 С крайне низкой вероятностью новый turn получает событие старого runtime await disposeRuntime либо сначала detach activeRequestId перед dispose
Утечки ресурсов
MEDIUM permissionWaiters утекают при queue overflow (таймер на 30 минут) daemon.mjs:269-270 Медленный рост памяти + возможный double-resolve При queue overflow синхронно очищать все pendingApprovals + permissionWaiters этой session
MEDIUM После таймаута future _responses вызов set_result в reader бросает InvalidStateError и убивает весь reader agent_sdk_bridge.py:396-406, 280 Крайне низкая вероятность, но фатально: после смерти reader все session не могут получать события Обернуть set_result в reader в try/except InvalidStateError
Оптимизация задержки
HIGH Нет прогрева preconnect, первое сообщение терпит 2-5 секунд холодного старта SDK daemon.mjs handle() После создания сессии Code пользователю приходится долго ждать перед отправкой первого сообщения Добавить method:'preconnect', Python вызывает его уже при создании сессии, заранее создавая runtime
MEDIUM Нет прослушивания событий между turn (perpetual reader) daemon.mjs readRuntime() После фонового завершения субагента пользователю не приходит уведомление, результат виден только при следующем взаимодействии После завершения turn поддерживать цикл query.next(), полученные события push-ить в Python новым типом сообщения
LOW Таймаута shutdown в 2 секунды часто не хватает, graceful close пропускается agent_sdk_bridge.py:611-617 При перезапуске процесса соединение SDK обрывается жёстко Увеличить таймаут до 5 секунд либо регулировать динамически по числу runtime

HIGH subprocess.run блокирует цикл событий до 5 секунд server.py:362 При первом streaming-запросе все параллельные потоки SSE и HTTP-ответы замерзают на 5 секунд Заменить на asyncio.to_thread(subprocess.run, ...) + кэшировать результат (логика кэша есть, но первый вызов всё равно блокирует)
HIGH append_event() — синхронная запись в файл + SQLite insert, вызывается на каждое событие SSE server.py:1560-1569 200 событий = 200 блокирующих I/O; поток SSE дёргается, на мобильных заметно Обернуть в asyncio.to_thread() либо писать пакетами (накопить N записей и сбросить разом)
HIGH load_events() синхронно читает весь файл JSONL server.py:1739-1753 JSONL длинной сессии — десятки MB; при stop_chat / восстановлении сессии цикл событий блокируется на секунды await asyncio.to_thread(load_events, path)
HIGH os.walk() синхронно вызывается в эндпоинте file-tree server.py:9896, 9729 Сканирование крупного repo (десятки тысяч файлов) блокирует на сотни ms, всё это время SSE перестаёт отправлять события Обернуть в asyncio.to_thread()

MEDIUM _agent_sdk_context_usage_cache без верхней границы server.py:164 По одной записи кэша на session, никогда не удаляется Перейти на LRU (maxsize=500) либо периодическую очистку
LOW _mobile_login_failures не очищает уникальные IP server.py:117 В сценарии сканирования портов словарь растёт неограниченно Фоновая уборка, очищать записи старше окна
